# 00 — 产品章程（Product Charter）

## 1. 产品愿景

建立一个内部项目工程管理中台，使用户能够远程提出需求，由多个 Agent 协作完成分析、规划、开发、审查、测试、人工验收和代码集成。

中台的价值不是替代 Codex 或 Claude Code，而是把这些 Harness 组织成可管理、可追踪、可恢复的工程执行系统。

## 2. 核心用户

- Owner：系统所有者，负责目标、重要决策和高风险审批。
- 项目维护者：维护项目资料、需求和项目规则。
- 测试人员/协作者：执行人工验收、提交反馈。

第一版可以只有 Owner 一个实际用户，但数据模型应预留项目角色。

## 3. 产品范围

### 3.1 中台负责

1. 项目导入和初始化扫描。
2. GitHub Issue 与中台 Web 需求入口。
3. 任务分类、Goal 规划和拆分。
4. Management Agent 的日常决策与协调。
5. 本地 Codex、Claude Code 进程与会话管理。
6. Git Worktree 管理。
7. 本地 Review 和 CI。
8. 远程预览和人工验收。
9. 自动创建 PR、Squash Merge。
10. Issue 状态更新、交付报告、归档和知识沉淀。

### 3.2 明确不属于中台

- 生产环境部署；
- 生产发布审批和执行；
- 生产环境持续运维；
- 面向第三方租户提供 Agent 执行服务；
- 自行实现基础模型或替代现有 Harness。

## 4. 核心产品原则

1. **本地执行优先**：代码、CLI、CI、预览环境运行在自有机器/服务器。
2. **Harness 可替换**：中台不绑定单一 CLI 的内部实现。
3. **中台掌握任务状态**：Agent 提交事件和结果，中台负责状态转换。
4. **人机分工明确**：低风险日常决策由 Management Agent 处理，关键业务与高风险事项由人决定。
5. **权限独立于提示词**：提示词不是安全边界，Policy Engine 和 OS 权限才是。
6. **全程可追溯**：需求、计划、决策、执行、Commit、CI、验收、PR 均可关联。
7. **动态任务层级**：简单任务直接 Work Item，复杂任务使用 Goal/Milestone/Work Item。
8. **滚动规划**：整体方向先确定，近期任务详细拆分，后续任务按实际进展细化。
9. **远程可验收**：用户不在执行机器旁边，也能通过私有网络查看预览并反馈。
10. **不把自动化等同于无人监督**：需要人工的事项明确等待，不伪造完成状态。

## 5. 成功标准

MVP 最重要的成功标准：

用户在远程电脑提交一个 Agent Issue，中台在本地启动 Codex 完成简单修改，并对候选 Commit 执行本地验证。人工验收通过后，中台冻结该 Commit、自动创建 PR，满足合并条件后默认使用 Squash Merge，并将结果记录到 Issue 和中台。参见 [ADR-015 代码交付与集成](adr/ADR-015-code-delivery-scope.md)。

## 6. 质量属性

- 可恢复：Daemon 或控制面重启后能够恢复任务状态。
- 幂等：重复接收 GitHub 事件、命令和合并请求不会造成重复副作用。
- 可审计：重要操作有操作者、时间、对象、依据和结果。
- 可隔离：不同任务至少有独立 Session 和 Worktree。
- 可扩展：未来可增加 Harness 和 Worker 节点。
- 可维护：第一版使用模块化单体，不提前微服务化。
