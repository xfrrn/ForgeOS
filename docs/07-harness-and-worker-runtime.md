# 07 — Harness、Worker Daemon 与会话运行时

## 1. 基本原则

- 每台本地执行服务器部署一个 Worker Daemon。
- Daemon 使用用户已登录 Harness 的非 root Linux 用户运行。
- Codex、Claude Code 在该用户下分别登录一次，任务复用现有登录状态。
- 不为每个项目/Execution 创建独立 Harness 账号。
- 每个写入型 Work Item 使用独立 Git Worktree。
- Session、Process、Execution 分开管理。
- 容器不是默认必选项；按任务风险和隔离需求启用。

- Worker Registry；

### 在工作台查看 Worker

执行节点启动时先向 `POST /internal/workers/heartbeat` 登记。节点在领取、执行和回报任务期间每 15 秒报告身份、操作系统、架构、逻辑 CPU 数、执行名额及启动时探测的能力。使用节点授权文件时，令牌只能为自己的节点 ID 登记。首次登记与最近心跳都按控制面数据库时间记录。超过 45 秒未收到心跳，工作台显示“心跳超时”；未结束的执行仍占用名额。

调度器对已登记节点取最近心跳与本次领取所声明能力的交集。节点重启或能力改变时先上报新心跳；一次领取可以主动缩小可承接任务的范围。仅对尚未登记的旧版 Worker 沿用领取请求中的能力声明。

Owner 在工作台点击“执行节点”，也可调用 `GET /workers`。列表显示节点最近一次报告和从执行记录计算的已占名额，服务重启后可复查。节点恢复时更新原记录。节点令牌仅用于内部操作，私网网关只代理列表的 Owner 入口。

执行记录中的工作区路径属于领取任务的节点。控制面接受 POSIX 根目录、Windows 盘符绝对路径和 UNC 共享路径，并按节点路径格式生成 execution 目录。Worker 执行前仍会在本机核对工作区及其授权的项目根目录。

普通执行和独立代码审查的领取响应保留登记时的仓库绝对路径，并附带 `repo_relative_path`，如 `team/beta`。当登记路径已在节点允许的根目录内且存在时，节点继续使用原路径。挂载位置不同时，节点在自己的 `FORGEOS_REPO_ROOT` 下按同一相对路径定位项目。解析后仍核对工作树顶层和 Git 管理目录的授权边界。

## 3. Harness Adapter

建议统一基础能力：
- Probe；
- Start；
- Resume；
- SendInput；
- Interrupt；
- Respond；
- Events；
- Status；
- Close。

可选能力：
- Steer；
- Fork；
- Native Goal；
- Usage Reporting；
- Queue Message。

Adapter 应报告真实能力，不支持的能力不得伪装支持。

普通 Worker 在启动时读取已配置 CLI 的帮助和版本。Codex 实现适配器检查隔离配置、工作区沙箱、JSON 事件以及按 Session ID 恢复的子命令；Claude Code 检查受限启动、工具范围、流式事件和恢复参数。只读 Codex 角色沿用结构化输出探测。探测依赖显式配置的可执行文件时，缺少必需能力会使启动失败。

Owner 在“执行节点”页查看每个适配器的版本和操作，API 字段为 `GET /workers` 的 `capabilities.adapters`。两种普通执行适配器当前报告 `probe`（检查 CLI）、`start`（启动回合）、`resume`（使用原会话发起新回合）、`events`（读取原生事件）。节点重新启动后，下一次心跳替换整份报告。老节点继续上报原有的任务能力字段。

启用 App Server 的 Codex 节点另报 `interrupt`，页面显示“中断回合”。该声明通过附加心跳查询参数传递，旧控制面忽略它并继续接收原有操作。切回 CLI 后，下一次心跳撤下中断能力。

在节点页可按适配器核对普通 Worker 启用的角色。API 在每个适配器的 `profiles` 下按 `implementation`、`planner` 保存最近心跳。版本 1 的 `version` 是整数，`permission` 是原生权限参数，Codex 另报 `sandbox`，Claude 另报 `tools`。Codex 实现使用 workspace-write，规划使用 read-only，两者审批均为 never。Claude 实现使用 acceptEdits，只启用 Read、Glob、Grep、Edit、Write。未探测到的角色不出现。旧节点的心跳会撤下上次报告的配置。

两种 CLI 通过同一个 Go 接口提供身份、版本和单回合执行。Codex 报告 `turn.failed`，或 Claude 报告失败的 `result` 时，Worker 保留模型失败及进程退出码，结束本次执行。Owner 可从失败任务发起新执行。若进程异常退出且缺少终态，适配器已确认可恢复的原生会话，Worker 会复核租约、Worktree 和起始提交，再从原会话重试一次。只读 Planner 还会检查工作树干净并清除上一次的临时输出。

## 4. Codex 接入建议

优先评估 Codex App Server，利用其原生 Thread、Turn、事件流、恢复、中断和审批机制。具体协议版本、方法名称和能力必须以实际安装版本的官方文档和探测结果为准。

普通 Worker 可设置 `FORGEOS_CODEX_TRANSPORT=app-server`，通过本地 stdio 执行 Codex 实现任务和只读 Planner。启动时检查可执行文件支持的参数。每回合核对返回的工作目录、Thread、沙箱、网络限制、可写目录和审批模式，再发送任务。事件必须属于当前 Thread 与 Turn，结构化计划只在该回合正式完成后保存。进程、会话及工具活动沿用任务的执行记录。未设置该变量时使用 `exec`。

App Server 使用当前 Harness 身份的登录状态，按角色固定 `never` 审批和沙箱。进程禁用 apps、plugins、hooks、MCP 和网页搜索，设置本次基础指令与空开发者指令，关闭自动载入项目指令。beta #168 已从正式 Worker 完成实现、Owner 退回、返工期间原生进程被终止后的同 Thread 恢复，以及 PR #169 的必需 CI、合并和 Issue 关闭。只读 Planner 已返回固定计划并在 Chrome 回读。该接入已验证版本为 `0.169.0-alpha.11.1`；正式运行中输入已由 beta #250 验收，原生工具审批仍待验收。[逐项证据](acceptance.md)

工作台暂停或取消 App Server 回合时，适配器在已核对 `turn/started` 后向当前 Thread 和 Turn 发送 `turn/interrupt`。收到匹配终态后关闭进程，沿用原来的暂停检查点或取消结算。尚未确认活动回合、请求失败或五秒内未退出时，使用进程终止兜底；取消后的输出不会成为候选。beta #170 已从 Chrome 暂停、重启控制面、恢复原 Thread，并经 PR #171 完成交付；只读 Planner 同样恢复到原 Thread 产出草案。beta #172 从 Chrome 取消，工具子进程退出，后续任务取得已释放资源。三次原生会话均记录了 `turn_aborted`、原因 `interrupted`，正常中断进程的退出码均为 0。

在已登录的 Harness 用户下执行 `python scripts/probe_codex_app_server.py --bin <原生可执行文件>`，通过本地 stdio 启动两个独立 App Server。探测核对服务返回的只读 sandbox，完成首轮后关闭进程，在第二个进程恢复原 Thread 并读取随机标识，再中断第三轮。以返回的 Turn ID 和 `turn/completed` 状态核对中断。当前实测版本要求先接收 `turn/started` 通知，再调用 `turn/interrupt`。可用 `codex app-server generate-json-schema --out <目录>` 对照安装版本的字段。[App Server 协议说明](https://developers.openai.com/codex/app-server/)

同一命令加 `--reconnect` 可验证原生进程仍在执行时的连接恢复。该模式需要 Python 包 `wsproto`，在临时私有目录启动独立的 App Server，用两个先后启动的原生代理连接同一套接字。探针在只读命令执行期间关闭第一条连接，从第二条连接读取原回合并追加输入，核对命令退出码、原生消息编号和最终回复。正式 Worker 的 stdio 进程恢复另行验收。[重连实测](acceptance.md#native-active-reattach)

用同一命令加 `--approvals` 实测命令审批。探针在只读 Thread 中用 `accept` 批准一次只输出随机数的 Python 命令，核对工具项状态和标准输出，然后在同一 Thread 再次提交相同命令，核对新的审批请求并拒绝。接下来分别拒绝和取消临时目录中的标记脚本，检查标记文件始终不存在、拒绝后回合完成、取消后回合中断。每次审批均比对工作目录、命令、Thread、Turn 和工具项编号。输出保留原生回执。

同一探测命令加 `--steer` 可实测运行中输入。在只读 Thread 的 turn/started 后，探针先核对不匹配回合的拒绝，再用 expectedTurnId 和 clientUserMessageId 将随机文本送入当前回合。第二个 App Server 从 thread/read 核对原生输入和回复。当前安装版本允许同一 clientUserMessageId 多次进入同一回合，响应丢失后的恢复需要先对账。普通 Worker 的 Owner 运行中输入见下方工作台记录。[协议实测](acceptance.md#native-steer-probe)

在任务详情展开活动执行，支持实时输入的 Codex App Server 会显示“当前原生回合输入”。提交后查看执行中的输入记录，可区分等待节点领取、已领取待确认、原生接受和原生拒绝。每个实例最多接收八条输入，每条最多 4096 字节；同时保留原有“下一回合指令”入口。输入绑定执行、节点进程实例、Thread 和 Turn。旧 Worker、两个 CLI 传输以及已结束或暂停的回合继续使用已有操作。

Owner 使用 `POST /executions/{id}/turn-inputs` 提交 instance、session_id、turn_id、UUID key 和 body。同一次提交重试沿用同一 key 和正文。Worker 使用已绑定项目和执行的租约领取，丢失领取响应时沿用同一领取编号重试。原生进程只发送一次 turn/steer；原生响应先写入节点私有 SQLite，再向控制面补报，直至取得确认。如果节点在发往原生进程后、保存响应前终止，记录显示“节点已领取，投递待确认”。可用原 Thread、Turn 和消息 key 核对历史；恢复任务不会把该输入自动投向另一个回合。[真实工作台验收](acceptance.md#live-workbench-turn-input)

原生回合确认完成或中断时，Worker 正常关闭输入并等待进程退出。App Server 拒绝中断或超时、需要强制终止时，Worker 先终止自己启动的进程，再关闭协议管道，避免 EOF 使强制终止被记录为正常退出。[中断回归与真实节点操作](acceptance.md#native-interrupt-fallback)

普通 Worker 的领取结果可包含 `record_app_turn`。当 Codex App Server 返回与本次 Thread 和 turn/start 一致的 turn/started 时，Worker 把 Turn ID 持久化到该进程实例。在任务详情展开执行尝试，可从运行中的观察及完成后的进程回执查看“原生回合”。同一实例已确认的编号不能改写；CLI、旧节点、旧控制面签发的作业保留原有记录。[原生回合身份验收](acceptance.md#worker-app-turn)

## 5. Claude Code 接入建议

第一版可评估 Headless CLI + stream-json + Session Resume；复杂交互可后续评估 Agent SDK。必须通过真实环境验证会话恢复、问题交互和权限事件。

在已登录的 Harness 用户下运行 `python scripts/probe_claude.py --bin <原生可执行文件>`。探测会发起两次真实模型调用。第一次在临时目录启动会话，接收并回答 AskUserQuestion，拒绝 Write 权限。第二次启动新的 CLI 进程，按 Session ID 恢复，要求返回第一次消息中的随机标识和选择的答案。脚本核对答复、权限请求的目标路径和文件实际状态后输出版本、Session 和两个 PID。Windows 上将 `--bin` 指向原生 `.exe`。

追加 `--interrupt` 可单独验证文本生成期间的原生中断。探针在同一会话收到首个文本增量后，经标准输入发送 interrupt，核对相同请求编号的成功响应、原生终态及进程退出码。[实测](acceptance.md#claude-stream-interrupt) · [Anthropic SDK 控制协议实现](https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/_internal/query.py)

普通实现 Worker 探测到 Claude 的流式输入选项后，在一个进程中仅提交一个用户回合。Owner 从工作台取消或暂停时，若已确认原生 Session，Worker 发送中断请求。节点核对成功回执与终态并记录退出码。进程尚未初始化、回执无效或五秒后仍未退出，会触发强制终止。旧节点继续按原方式取消；工作台根据节点心跳展示适配器的中断能力。[工作台实测及暂停后的外部阻塞](acceptance.md#claude-worker-interrupt)

### 将实现任务交给 Claude Code

在 Worker 专用账号的环境中设置 `FORGEOS_CLAUDE_BIN` 为本机 Claude Code 可执行文件；Windows 使用原生 `.exe`。Worker 启动时检查版本、`--restricted` 和 `--safe-mode`。通过探测的节点才会声明 `supports_claude`。模型认证沿用服务账号的登录或专用用户设置。用户设置位于该账号的 Claude 配置目录，受限模式下由 Worker 显式传给本机 CLI。[Claude Code 设置来源](https://code.claude.com/docs/en/settings)

Owner 可在导入 Issue 时提交 `{"validation":"auto","harness":"claude"}`，也可在预览反馈的独立工作项表单选择 Claude Code。显式选择优先于项目默认。新任务将 Harness 选择与 Issue 快照一起冻结，重复导入复用原记录。Claude 节点执行实现与退回修订，计划任务继续由具备只读规划能力的 Codex 节点领取。既有的仅验证任务沿用原候选。

项目可在仓库根目录提交版本 1 的 `project.yaml`，在 `execution.default_harness` 填写 `claude` 或 `codex`。手工导入和带 `forgeos-agent` 标签的自动派发均读取登记克隆的固定基础提交。没有声明时默认 Codex。任务详情内的“项目执行配置”显示实现 Harness 与文件的 Git blob。工作区未提交的改动不会改变配置来源。规划任务使用项目默认值为后续写入型子项选择 Harness。[项目配置示例](../schemas/project.yaml.example)

执行时 CLI 使用文件读取、搜索和编辑工具，限制在工作树内；Worker 禁用扩展自定义、MCP 和浏览器集成，并传入选定的系统和模型环境变量。CLI 结果中的原生会话编号、实际版本和候选 SHA 在任务详情可查看。提交、验证、验收与 GitHub 交付沿用原有工作项流程。

## 6. Session 与 Process

- Session 是 Harness 原生持续上下文。
- Process 是 OS 进程实例。
- Execution 是中台一次工作尝试。
- 一个 Execution 可以经历多个 Process Instance。
- 普通等待、回答和进程重启不自动创建新 Execution。
- Session 丢失时用 Handoff Context 创建新 Session，并保留关联。

只读 Planner 进入主动暂停前，Worker 将冻结的讨论、Thread、工作区身份、Git 树、剩余执行时间和资源阶段写入节点日志。原生规划恰好完成时也保存已验证的草案。写入型任务使用同一节点日志和恢复领取机制，另保存原检查点的输入及尚未提交的业务问题。当实现回合已经完成时，恢复后继续处理该回合的结果。原租约有效且节点身份和工作目录一致时，重启的 Worker 等待 Owner 恢复，核对版本和工作区后继续。并发接回时，控制面只允许一个进程领取本次恢复；Owner 在等待期间取消则直接结算任务。

Codex 写入回合与只读 Planner 从 CLI 的 `thread.started` 获取 Thread ID。两者共用进程登记与退出回执，保留原生版本号、PID 和每轮实际会话。独立 Management 计划审核也记录节点、进程、原生会话、退出和公开消息，见下节；其他独立调用仍沿用各自的回执。

已确认原生 Thread 的 Codex 进程异常退出、且事件流中没有终态或明确报错时，Worker 重新确认租约、工作区身份和起始提交，用相同权限执行一次 `codex exec resume <thread>`。写入回合保留未提交的编辑。只读规划还要求工作区干净，并清除上次生成的临时输出，重新验证恢复回合生成的结构化计划。

在任务详情的执行记录查看“最近的节点进程报告”。正在运行的页面每 8 秒读取最新任务；也可手动刷新。工作台显示节点、实例号、PID、Harness 版本、已确认的原生 Session、进程开始时间及控制面收到报告的时间。报告反映节点上报时的状态。失联时保留最近一次观察和原执行的租约状态。收到最终结果后，页面显示完整的 Harness 进程记录。

具备实时上报能力的控制面在模型任务的 claim 响应中返回 `report_live_process`。Worker 在 SQLite 记录启动、原生会话和退出后通知上报循环，并每 15 秒重读最近进程。通过 `POST /internal/executions/{id}/process` 发送执行租约令牌和 process 对象。节点需要对应项目与执行权限；控制面核对租约、任务指定的 Harness、进程身份与时间顺序，拒绝过期租约和旧状态重放。上报失败时，下一次从本地日志重读。此请求独立于租约续约和最终回执。

控制面在普通模型任务中通过 `record_tool_activity` 请求采集工具事件。在“最近的节点进程报告”查看工具名、调用编号、节点时间和开始、输出更新、完成或失败状态。调用编号取第一次观察到该调用的事件序号，同一进程中的并行调用可分别追踪。只有终态事件的工具也会显示。执行结束后，在“Harness 进程记录”展开对应进程继续查看。每个进程显示最近 32 条事件，窗口移过开头时显示事件总数。Worker 本地 SQLite 保存该进程从开始采集起的全部工具事件。

Codex 从 `item.started` 和 `item.completed` 识别命令执行、文件修改等已知类型。Claude Code 从 `tool_use` 和同一调用的 `tool_result` 记录已授权工具。事件字段只含序号、调用编号、工具类型、状态和时间；命令、参数、路径、正文与工具输出均不进入此记录。旧版 Worker 留下的进程记录可继续读取。

普通实现与只读 Planner 可通过 record_tool_output 领取能力采集完成后的工具结果。本项 Codex 命令结果从 CLI 的 aggregated_output 或 App Server 的 aggregatedOutput 读取；Claude 读取已授权工具调用的 tool_result 字符串或 text 块。每个进程保留最近一次有正文的工具结果最后 8 KiB，绑定工具名称、调用编号及完成事件序号；空结果保留前一份有正文的记录。调用参数与非文本块不进入该窗口，正文内普通路径仍可显示。

节点复用公开消息的脱敏器，先遮蔽已知凭据和私钥，再把工具事件和输出原子写入 SQLite。分多次读取私钥时，遮蔽状态持续到结束标记；状态按执行租约摘要和输出类别保存在 harness_output_redaction，与输出同一事务写入，恢复节点日志后继续遮蔽。任务页从“最近完成的工具输出”查看；重启及最终回执沿用同一份记录。控制面校验事件关联、序号、租约和退出状态，最终回执不得删除或改写已观察的输出。进程接口允许最多 128 KiB 的 JSON 请求，以容纳两个 8 KiB 窗口经 JSON 转义后的正文；各正文的 8 KiB 限额保持有效。旧控制面未声明采集时不发送新字段，旧 Worker 的历史保留缺省。

beta #200 已从 Codex 原生回合核对：工具先读取合成私钥的前半段，Owner 在有界观察等待期间暂停；Worker 与控制面重启后，替代进程在原执行、Thread 和工作区只读取后半段。节点从 SQLite 恢复遮蔽状态，直到结束标记才解除；任务历史保留两个原生 PID 的各自输出。beta #202 另从 App Server 的活动暂停和 Worker 替换复验；beta #204 从 Claude 的业务问题检查点、Worker 替换和 Owner 答复复验。同一原生会话的替代进程只读取后半段，仍继承 SQLite 的遮蔽状态。Claude 本项未覆盖活动工具中的强制中断。

App Server 的普通实现和只读 Planner 还可通过 record_tool_stream 领取能力处理 item/commandExecution/outputDelta。节点核对 Thread、Turn 与已开始的命令调用，按完整行脱敏，更新该调用的最近 8 KiB。输出更新使用同一工具事件序列的 output 状态；tool_output.partial=true 表示尚未收到完成结果。收到终态后保存已采集的安全窗口及最后未换行的一段，清除 partial；不重放可能截断的原始聚合正文。多个调用各自保留窗口，进程报告仍只显示最近一次更新的调用。

任务页显示“工具输出片段（未收到完成结果）”，暂停或进程退出不会被补造为工具完成。beta #207 从 Chrome 观察到命令结束前 45.61 秒的脱敏输出并重启回读；beta #209 在同一命令读取私钥前半段、仍等待时暂停，更换 Worker 后在原 Thread 只读后半段，节点继续遮蔽，历史保留原进程的未完成片段。新旧组件双向组合和新只读 Planner 已实测。

未换行的原始片段仅在内存中暂存，最多 64 KiB；超过上限的整行丢弃并保守遮蔽后续输出，直到明确的私钥结束标记。节点日志只保存脱敏窗口和可能有未结束敏感内容的布尔状态。即使只收到半个开始标记便退出，替代进程也会保守遮蔽；该分块中断边界由回归覆盖。正常收齐一行后会解除单纯由未换行引起的不确定状态。换行前的等待与异常退出时丢弃未完成原始行是有意的保护边界。

该窗口不是完整工具会话归档。Codex CLI 与 Claude 当前仍采集完成结果，不宣称具备此 App Server 通知能力；它们的其他增量接口需要分别验证。Codex MCP 等结构化结果与中央全文归档仍待补齐；本地文本归档和保留策略见下文。

普通实现与只读规划的领取响应通过 `record_model_output` 开启公开消息记录。Codex CLI 的已完成 agent_message、App Server 的已完成 agentMessage 和 Claude 的 assistant 文本块进入同一份进程输出；思考块、工具参数及用户输入不进入这份记录。每次完整消息到达后更新，节点在写入 SQLite 前遮蔽可识别的敏感行、执行租约、当前及已观察的轮换节点凭据，以及敏感环境变量的值。页面窗口为每个进程保留最近 8 KiB 和递增序号，节点完整公开文本另按下文归档。

运行中从任务详情“最近的节点进程报告 → 模型公开消息”查看；结束后从“Harness 进程记录”回读。输出沿用进程上报的项目权限、租约与身份检查，同一实例拒绝旧序号、同序号改写和退出后改写；最终回执也不得删除或回退已上报的公开消息。控制面重启后可回读，最终记录随原结果缓冲、重报并归档。旧控制面未声明采集时，新 Worker 沿用原协议；旧 Worker 及历史记录不补造输出。内置 go-test 的实时输出也已从既有 CI 通道验收；完成后的工具正文也已从三种原生适配器验收；App Server 命令增量输出也已单列验收；固定提交的 Local Mock / Integrated 启动检查已从工作台、命令行和真实 Docker 验证实时日志与终态回读，包含依赖故障、取消及立即退出。其他适配器的增量能力继续待验收；独立角色进程见下文。

正式 Worker 通过 Claude Code 的 `stream-json` 读取原生初始化和终态事件。SQLite 的 `harness_processes` 为每个启动的适配器进程记录本地实例号、PID、探测到的版本、开始时间、CLI 确认的 Session、退出时间与退出码。使用原生可执行文件时，该 PID 即 Claude 进程的 PID。通过租约摘要关联 `attempts` 下的同一次执行。

若已确认 Session 的进程以非零状态退出，且没有收到终态，Worker 等待旧进程退出，向控制面确认原租约，核对原工作区、分离 HEAD、Git 目录和起始提交后，使用相同工具权限与 `--resume <session>` 恢复一次。恢复提示要求先检查现有编辑，再完成剩余工作。已报告的模型失败、身份不符、失去租约、变更起始提交或取消中的任务保留失败状态。一个执行无需为这次恢复创建新的 Worktree。


## 7. Checkpoint

至少保存：
- Execution ID；
- Harness 类型、版本；
- Native Session ID；
- Worktree ID、路径、分支；
- Base Commit；
- Requirement Revision；
- Plan Revision；
- 最后事件序号；
- Pending Request；
- 当前状态；
- 是否可恢复。

## 8. Workspace

每次写入型 Execution 记录实际使用的 Worktree、分支、Base Commit、路径、Diff 状态和生命周期，确保不同写入型 Work Item 的改动彼此隔离。同一 Work Item 重试时是否复用之前的 Worktree，见[待细化事项 B.5](16-open-decisions.md)。

审查任务使用固定 Commit 的只读工作区。测试任务使用固定版本的测试工作区。

## 9. 进程和资源

- Daemon 由 systemd 运行；
- 不以 root 执行 Agent；
- 显式设置 HOME、PATH、代理和工作目录；
- PID 不是 Session 身份；
- 资源不足时排队；
- 进程退出不等于任务完成；
- 不允许因为租约丢失而盲目重复执行。

## 10. 恢复策略

Linux Worker 为原生回合创建独立进程组。回合被取消、事件解析中断或启动后的登记失败时，Worker 终止该组，包括仍在组内运行的工具。

运行中每个执行凭自己的租约令牌独立续约。有效期内的短暂断线可以重试；永久拒绝或超过已确认的截止点会取消该执行的上下文。控制面保存原执行与工作区，由 Owner 核对处置。具名节点可在原租约续约和 CI 上传期间轮换身份令牌。使用节点令牌文件，并按[重叠授权、切换、撤销的顺序](local-development.md#为多个-worker-分配项目)操作。[租约接口与时间窗口](local-development.md)

Worker 已支持执行结果断线缓冲和重启补报。查询本机领取记录、未确认结果和冲突回执的方法见[Worker 执行恢复日志](13-data-storage-and-audit.md#worker-执行恢复日志)。

实现回合等待业务答复时，Worker 随问题登记暂存区和工作区两棵 Git 树的 SHA。工作区树包含 Git 会暂存的新增、修改和删除。Owner 可从任务详情核对两者。答复后，Worker 在原租约和工作区中重新计算这两个 SHA；任一变化都会使该次执行失败，保留工作区供核对。Owner 可从失败执行重试，取得新的工作区。

若 Daemon 在这个检查点退出，在租约到期前以相同配置启动 Worker，可接回原执行。接回时沿用剩余执行时间与资源申请序号，核对 Harness 版本和 Git 工作区。若同时启动两个替代进程，控制面只允许一个取得答复并恢复原会话。已领取答复的进程在启动下一回合时中断，或租约已过期，须核对现场后再处置。

接回业务问题后，Worker 用原 Session 处理答复。若原生客户端明确报告该 ID 缺失，Worker 在同一工作区再次核对执行租约、Git 目录、起始提交及提问时保存的两棵树，再将已确认的检查点输入和当前答复交给新会话。控制面把这次交接关联到已领取的答复、提问进程和下一检查点。任务详情保留提问进程、恢复失败的进程和接手的进程。

- Harness 进程崩溃：尝试恢复原 Session；
- Daemon 重启：恢复执行记录、Worktree 和事件；
- 服务器重启：检查工作区、租约、Session；
- Session 不可恢复：创建 Handoff Context；
- 对迁移、部署等非幂等操作，恢复前必须检查实际副作用。

写入进程在回合中异常退出时，Worker 在尝试恢复原会话前记录暂存区和工作区两棵树。如果原生恢复命令随后确认会话缺失，控制面在仍有效的模型资源与执行租约内登记两次退出回执。Worker 再次核对两棵树，将原进程最后的工具事件、草稿位置及冻结输入交给新的写入会话。终态进程历史必须能逐项匹配这些回执。

Codex 0.169.0-alpha.11.1 和 Claude Code 2.1.310 均已实测识别原生会话缺失。Worker 只在恢复命令退出码为 1、原生客户端尚未确认会话，而且缺失回执包含本次请求的确切 ID 时记录该原因。任务详情可区分会话缺失与普通回合失败。

只读 Codex Planner 确认原 Thread 缺失后，Worker 再次确认执行租约、原工作区、固定提交和干净的 Git 状态，清除上次规划的临时输出，在同一工作区以只读、禁网权限启动新 Thread。新输入保留原规划请求和讨论，并写明来源 Thread、执行编号和固定提交。任务详情的进程记录可回查两个 Thread 及中间失败的恢复尝试。

Codex 或 Claude Code 实现任务在首个检查点主动暂停后，也可从缺失的原生会话交接。Worker 在恢复命令确认缺失后复核租约、Git 目录、起始提交、暂存区树和工作区树。新会话取得这些树的标识和冻结的任务输入，在原工作区检查现有草稿后继续。控制面将来源进程与同一执行中 Owner 已恢复的暂停记录核对。

在后续检查点，支持交接的 Worker 会按序重读已确认回合的冻结讨论、Owner 指令和已答复的业务问题，并分别标明当时的会话、指令和答复来源。当前回合仍使用暂停时冻结的输入。控制面在同一事务内登记暂停来源、新会话及接收检查点，确认该回合；候选审核仍可回查每条指令实际进入的会话。beta #151 从 Claude 检查点 2 核对了早期的 Owner 答复。beta #153 从 Codex 检查点 2 核对了独立 Management 的 D1 答复、原决定和适用范围。

### 独立角色进程

新 Management Worker 在领取请求声明 supports_plan_review_process，控制面为 Goal 计划审核返回 capture_process；共享资料审核通过独立的 supports_share_review_process 声明同一采集能力。该角色继续使用只读、禁工具、never 审批的原生 Codex，不读取实现工作区。工作台的各版 Goal 计划显示“Management 审核进程”，含节点、PID、版本、Thread、开始及退出时间、退出码和最近 8 KiB 的公开消息。记录反映最近观察，未收到退出回执不能当作仍在线的保证。

采集复用普通 Worker 的进程日志和先脱敏后入库的公开消息窗口。节点 SQLite 以 management-<节点名> 区分角色；节点名使用 FORGEOS_WORKER_ID，未设置时使用主机名。每个审核租约有独立记录，租约重发及新修订不会覆盖旧尝试。Worker 每 15 秒或进程更新时上报；退出回执确认后才发送审核结论。控制面校验项目、修订、租约、节点和进程连续性；已观察的成功退出会话必须与审核结论一致。

原生异常退出保留实际退出回执，不生成审核结论；后续修订可由新会话继续审核。旧控制面／新 Worker、新控制面／旧 Worker均保持原协议，不补造进程。当前覆盖计划、共享资料审核、仓库分析、业务问题建议、反馈分类、知识提取审核、候选测试计划生成与覆盖审核及独立 Reviewer，已支持下文所述已记录原生 Session 的 Daemon 恢复；本地公开消息归档见下文，中央全文归档仍待补齐。

共享副本的来源项目可在详情及发出列表展开同一“Management 审核进程”。观察绑定副本 ID、审核租约和来源项目；请求不得同时指定计划与副本。Owner 在回合中撤销副本后，实际进程仍可回报退出，但不能生成已撤销副本的审核结论或发布；账号名额在完成回报后归还。接收项目的经验接口仍只返回原有五个副本字段，进程、会话、公开消息和审核笔记均留在来源项目。

仓库分析通过 supports_analysis_process 协商采集，观察绑定初始化清单任务及本次分析租约。清单中的“Management 归纳进程”展示所有尝试，失败后点击“重新归纳”使用首次保存的来源，不读取克隆的新 HEAD。失败回报必须对应已退出进程；成功报告还须匹配退出码 0 和原生会话。失败尝试、新会话及公开消息不会被重试覆盖。新旧组件双向组合、真实原生异常退出、固定来源重试和控制面重启均已验收。

业务问题审阅通过 supports_question_process 协商采集，进程只绑定该问题及本次建议租约，不与提问执行的实现进程混合。“待答问题”和任务详情可展开“Management 问题审阅进程”。已观察的回合须确认退出码 0 和同一原生会话后才接收建议；D1 引用已有决策也遵循该条件。Owner 提前答复或问题撤回后，仍可记录在途回合的实际退出，迟到建议不会覆盖答复；成功完成回报释放所占名额。异常退出只保留失败观察，不生成建议，未完成租约按原有期限释放或重新领取。

预览反馈分类通过 supports_feedback_process 协商采集，观察只绑定反馈 ID 和本次分类租约。反馈页的“Management 分类进程”显示各次尝试；分类写入前锁定反馈，核对实际退出码 0 和原生会话，再按既有规则检查观察引句、固定候选及与实现会话的独立性。异常退出不生成分类；六分钟租约自然到期后，新会话可重领原反馈，旧失败记录保留。分类本身仍不批准候选。

知识提取的 Curator 通过 supports_process 声明采集，知识审核的 Management 通过 supports_curation_process 声明采集。两者使用各自凭据上报，分别写入 curator-<节点名> 和 management-<节点名> 的私有 SQLite。知识提取与审核页分别展示两类进程，成功结果必须匹配实际退出码 0 的原生会话。Curator 因引文不连续而重跑时，同一租约最多保留两次原生尝试；第二次须在第一次成功退出后开始，最终提取只接受最后一次尝试的会话。失败、空提取和后续资料修订各自保留历史，不把退出或提取结果当作经验审核批准。

候选 Test Agent 以 supports_process、Management 以 supports_test_plan_process 协商采集，各自凭据仅可上报本角色。test-agent-<节点名> 与 management-<节点名> 分别保存节点日志；控制面绑定测试计划 ID、角色及租约。各版候选测试计划分别显示两类进程并自动刷新待完成记录。新修订替代在途旧修订后，旧进程仍上报实际退出；完成回报仅归还名额，不发布过时计划或覆盖结论。成功回报必须匹配退出码 0 及原生会话；失败回报也必须先确认已观察进程退出。失败状态保留真实退出和公开消息，Owner 可生成新修订继续。独立 plan-tests 与 review-test-plan 命令仍按原协议输出结果。

独立 Claude Reviewer 通过 supports_process 协商采集，以 stream-json／verbose 读取原生初始化、公开 assistant 文本和结构化终态。仍使用无工具、dontAsk、禁 MCP 扩展和浏览器的角色配置，不采集 thinking 或工具载荷作为公开消息。reviewer-<节点名> 的私有 SQLite 与其他角色分开。观察绑定原候选执行及审查租约，成功审查必须匹配实际退出码 0 和会话；失败回报也需先确认已观察进程退出，才能记录失败并释放名额。Owner 从“查看审查记录”读取运行中、失败和最终历史，在失败后点击“重试审查”会创建新租约和会话，保留旧记录。旧组件与独立 review-candidate 命令继续使用原最终 JSON 协议。

### 独立角色的已完成结果补报

Management、Curator、Test Agent 和 Reviewer 在发送最终结果前，将原请求正文写入同一身份的私有 SQLite。来源包括计划／共享审核、问题建议、反馈分类、仓库分析、知识提取与审核、候选测试计划与覆盖审核、独立代码审查。Daemon 启动时先处理待补报结果，再领取新作业；使用原接口、原租约及原会话，不再次调用模型。控制面仍按既有项目、租约、进程退出、来源与结果校验决定是否接收。

HTTP 204 表示已确认，409 表示结果与当前状态冲突，两者均结束本次补报。确认后删除待发正文；冲突只在私有日志中保留去掉租约字段的原结果。未收到响应、5xx 等临时错误继续重试；鉴权及其他非临时错误保留待发结果并退出，修复配置后重启可继续。相同租约和结果端点不能写入不同正文。日志按控制面地址、节点名和角色隔离；凭据轮换后仍用同一身份补报，不把凭据写入补报记录。

此机制从最终结果已持久化开始提供恢复。模型启动前的已领取作业另由下述冻结日志恢复；已成功退出并持久化结构化输出的回合另见下述回合恢复；原生回合仍在运行、输出尚未持久化等窗口仍需后续原会话恢复。不得把已完成结果补报记为完整的角色进程恢复。

独立角色的实际退出另存入 role_process_receipts。网络失败不再把已经完成的模型结果改判为模型失败；节点保存最终结果后，先补报实际退出，再发送结果。Daemon 启动及每次领取前处理遗留退出，Curator 引文修复的第二回合也不能越过第一回合的退出确认。204 结束退出补报；409 将去租约的冲突观察留在私有日志，并继续由结果端点判断最终回执。鉴权等非临时错误保留待发退出并停止领取。模型真正失败时仍保留原始失败，不据此补造成功结果。


### 独立角色的领取响应重放

四类角色在发起领取前，将随机请求编号、完整路径及请求正文写入自己的节点 SQLite。请求携带 X-ForgeOS-Claim-Key 和 X-ForgeOS-Node；控制面按项目、角色、节点和编号保存正式分配的原始响应。同一编号必须保持请求路径及正文相同。成功分配与响应快照在一个 PostgreSQL 事务中提交；空轮询不冻结队列。

网络中断或 Daemon 重启后，节点先重发待确认领取。控制面返回同一份作业、能力配置、租约和原截止时间，不再次占用模型名额或延长租约。Management 的候选来源查询使用同一外层事务；未找到作业的来源回滚到保存点，释放该候选的模型预算锁，再尝试下一来源。

节点只在完整解析 200 响应或收到 204 后移除待领取记录；两个 Daemon 共用同一节点日志时，只有一个可消费相同分配。已过原截止时间的回执仍带原期限，遵守既有回合 deadline 和控制面结果门禁。完整作业与领取记录的确认在同一节点事务内切换，恢复规则见下节；已经开始的原生 Session 仍需后续恢复。

不携带编号的旧 Worker 沿用原领取协议。新 Worker 可接收没有编号回显的旧控制面响应，但旧控制面不提供原子领取重放保证。升级时保留节点地址、身份和私有状态目录；代码变化后也先发送已保存的旧请求，不能用新能力声明替换同一编号。

### 模型启动前的独立角色作业恢复

四类角色完整解析领取响应后，在同一 SQLite 事务中移除待领取请求并保存原始作业、租约摘要和本次 Daemon 标识。Daemon 重启时，先补报已有退出与最终结果，再读取冻结作业。尚无原生启动标记的作业直接使用原响应继续，不再向控制面领取，也不更新来源、能力或租约期限。

正式角色 Daemon 对自己的日志文件持有操作系统排他锁，直到进程退出。同一控制面地址、角色、节点及状态目录只允许一个 Daemon；不同角色各用自己的锁。Windows 使用 LockFileEx，Linux 使用 flock；本次实测覆盖这两个平台。

启动原生模型前先持久化 started 标记。原 Daemon 正常结束本轮后可继续处理下一作业；如果换了 Daemon 且已存在启动标记，先检查成功完成快照；未完成回合只有满足下文原生恢复条件时才能继续，否则保留日志并明确报错停止，不能凭缺少 PID 或 Session 就再次调用模型。已获 204 或 409 的最终回执可结束旧作业。模型启动前的中断直接恢复；成功完成回合与已记录原生会话的恢复分别见下文。

### 已完成独立角色回合的恢复

启用了进程采集的正式角色，在原生进程成功退出且结构化输出解析成功后，把回合输出、原生 Session 和退出补报写入同一 SQLite 事务，再尝试发送退出及业务结果。此处保存的是模型输出；业务层继续使用冻结作业进行引文校验、测试用例绑定或结果组装，不跳过原有验证。

每次原生启动前，作业启动标记与该回合的待完成记录在同一事务写入。Curator 引文修复的两个回合分别保存；不允许重复启动同一回合覆盖已有输出。重启后，已完成回合使用原输出和 Session 继续业务层处理，不再启动模型；未完成回合另外核对原生恢复条件。先补退出，随后提交最终结果；旧修订仍由控制面拒绝。

作业结算或原 Daemon 正常结束这一轮后，下一次领取在同一事务删除作业及临时回合输出。角色进程历史和最终回执保留。没有进程采集的旧控制面协议、还未保存成功快照的回合、原生进程仍在运行的情况不享有本项完成恢复保证。

### 独立角色的原生 Session 恢复与交接

四类正式角色通过 supports_role_resume 协商，控制面把 recover_native 写入原子保存的领取响应。节点在私有角色日志目录中保存工作目录、Harness 版本、首次提示及输出合同。Daemon 重启后，已记录 Session 的未完成回合在原租约期限内使用相同工作目录、冻结输入和原生 resume 参数继续。原进程仍存活时停止恢复，不另起模型；只能核实其退出后重启 Daemon。无法取得原退出码时明确记为 -1，不能作为成功。

原生 CLI 明确报告 Session 不存在时，保存该次实际失败进程，再在相同工作目录用冻结输入启动新 Session。新进程记录 handoff_from，控制面校验同节点、相同业务目标、前一进程退出及递增实例；工作台展示恢复来源、失败尝试和交接会话。模型业务失败不会据此转为成功，恢复仍受原期限及业务验证限制。新进程不能用旧成功进程绕过结果门禁。

已从 Chrome 和正式 Daemon 验证 Curator、Management 知识审核、Test Agent、Claude Reviewer 的原会话恢复，以及 Codex／Claude 的会话缺失交接。测试还覆盖同 Daemon 内原生子进程中断后恢复。缺少 PID／Session 的启动间隙、仍运行的 CLI 事件流接回、版本变化、工作目录丢失不能自动恢复，保留日志并报错。旧领取响应没有协商字段时沿用原协议。角色 Worker 在后续领取前按期限清理已结算回合的私有输入和工作目录；在途回合保留恢复资料。[清理与恢复](14-deployment-and-operations.md#role-recovery-retention)

### 节点公开消息与工具输出归档

已协商采集的模型公开文本、工具事件和文本结果同时写入私有节点归档。Codex CLI、App Server、Claude 及四类独立角色共用原有脱敏规则；只归档适配器实际收到的公开记录，不读取思考块、工具参数、用户输入或凭据。模型文本和已完成工具结果不再因 8 KiB 页面窗口丢失开头；App Server 命令增量按到达顺序保存新脱敏片段，完成事件不重复写聚合正文。未收到完成的事件仍是 output，不伪造 completed。

通过正式 Worker 的 process-logs 子命令列出、导出和清理本地归档，操作见[本地运行指南](local-development.md#导出和清理节点进程日志)。JSONL 导出包含进程、Session、适用的任务／执行编号、记录序号、工具调用编号、字节数和校验摘要。元数据及正文以同一 SQLite 快照导出；序号、字节或摘要不一致则失败，成功末行给出 verified。这是内容一致性校验，不是防篡改签名。

每进程默认最多 32 MiB，达到上限后保留连续前缀并累计省略记录与字节，导出明确标注 truncated。默认在业务结果确认 30 天后清理正文，保留摘要、计数、进程历史和已有页面快照。运行中、尚未确认、已暂停以及仍由独立角色作业持有的记录不清理。旧进程不会补造完整输出；CLI 会报告没有归档。

本项为节点本地归档，中央传输与工作台全文下载尚待补齐。原生工具自身未提供或已截断的输出、未收到的崩溃尾部不能重建；跨块敏感行继续遵循现有保守脱敏边界。角色恢复的冻结提示及工作目录仍按其单独生命周期保留。

### Codex 文件改动结果

已启用工具结果采集的普通 Codex 实现回合，还会把原生 file_change／fileChange 回执中的新增、修改、删除及移动路径写入同一工具窗口和节点归档。CLI 使用实际返回的清单；App Server 的原生 changes[].diff 还提供补丁正文。仅选择已知的路径、改动类型和补丁字段，不记录工具参数或调用输入，不为 CLI 推断缺失补丁。

只有原生完成或失败事件带来结果正文，started 不发布预期改动。失败和 declined 继续显示为 failed，不据此宣布文件已成功修改；候选仍须经过 Git 差异、验证和 Owner 验收。路径按原文加引号保存，匹配已知凭据时同时遮蔽其转义形式，正文沿用跨块脱敏规则。未知改动类型不生成伪造结果。

工作台仍从“最近完成的工具输出”查看，工具类型为 file_change；历史及 process-logs 导出使用相同调用编号和序号。当前支持已实测的 Codex 0.169.0-alpha.11.1。MCP、网页搜索和其他未授权工具仍保持原权限策略，不因采集新增授权。


### 普通 Worker 的候选结算恢复

启用检查点和模型名额管理的写入任务会在首次检出完成后、申请模型名额前保存起始 SHA、索引树、工作区树、Harness 版本和冻结的作业。首次名额响应丢失时，同身份 Worker 重启后先确认租约，再取回检查点 0，复核现场后请求同一步骤。Owner 在停机期间取消会阻止原生启动。[首个模型名额的恢复与取消](acceptance.md#first-model-grant-recovery)

管理模型名额的普通 Worker 在原生回合成功返回后、释放名额前，将 Session、资源步骤、冻结的评论和 Owner 输入、业务问题及 Git 树写入节点 SQLite。节点重启后先确认租约、原生版本和工作目录，再幂等释放同一步骤。若 Owner 已请求暂停，先保存暂停检查点并等候恢复；停机期间取消则结束执行。原回合的结果可以直接用于后续检查点。[真实回执丢失、暂停与取消](acceptance.md#returned-writer-recovery)

对于启用评论检查点的普通写入回合，模型完成且没有提出业务问题时，Worker 在确认当前检查点前保存原生 Session、回合序号、剩余时间、Git HEAD、索引树和草稿树。重启后先确认原租约，再按原序号向控制面确认回合并重新读取下一批输入。树和 HEAD 一致时，有评论或 Owner 指令就以原 Session 开始下一回合；输入为空就从已记录的树生成候选。排队等待下一回合的模型名额期间保留上一回合的恢复记录；即使控制面已经分配名额、节点尚未收到回执，也可重报同一资源步骤。真正交给适配器前再次核对 HEAD、暂存区和草稿树，并消费一次恢复记录。[模型名额回执丢失实测](acceptance.md#queued-model-grant-recovery)。[两次中断与实际交付](acceptance.md#completed-writer-input)

写入回合完成并处理完当前检查点输入后，Worker 生成候选对象，先将冻结作业、原 Worktree 身份、候选 SHA、原 Session 和资源步骤写入私有 SQLite，再把 HEAD 附到候选。重启同节点身份、同控制面 origin 的 Daemon 时，在领取新工作前检查这些候选，确认原租约仍有效、原仓库与工作目录相符、HEAD 是原位置或已记录候选、索引和文件树均等于候选。任一检查失败保留记录供核对，不重新运行模型或生成其他候选 SHA。

验证完成后先持久化成功或失败结果，再释放原 CI 名额。若最终结果尚未入队即退出，替代进程复用验证结果，仅幂等释放同一步名额并发送回执；没有保存验证结果时对固定候选重新验证。最终回执入队与删除候选检查点使用同一事务。每个 Execution 使用节点文件锁，第二个 Daemon 不能同时接回相同执行，不影响其他 Execution。

Owner 取消、来源关闭及验证超时仍回报失败或停止，不伪装成成功。被修改的工作区、失效租约及写盘失败保留待核对状态。此能力覆盖候选检查点已保存之后；更早的普通 Daemon 崩溃、无检查点的旧执行及整机重启仍未据此验收。旧 Worker 不识别新候选表，不应在存在该检查点时降级。

写入回合结束并处理完最后一批评论与指令后，普通 Worker 将原生会话、原 HEAD、索引树及完整草稿树保存到节点 SQLite。Daemon 或控制面重启时，Worker 先核对原租约和工作区，再用记录的树生成候选。候选 SHA 持久化后才更新真实索引与 HEAD。恢复中发现文件或索引被改动，将保留现场供核对。已有候选的旧节点记录仍可继续原验证。
