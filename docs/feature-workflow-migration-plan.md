实施规划 v2.1 · 2026-11-23 · ForgeOS 源码基线 `74a6789`

01–16 产品流程、AionUi/AionCore 功能讨论底座，以及以功能话题为入口的首版工作台设计均已确认。第 9 节记录实现默认值，第 10 节列出工程工单，第 11 节记录已确认的界面设计与各批验收场景。真实客户端续聊和 8080 工作台联调分别在 P0、P1 验证。

### 首批实现与实测 · 2026-11-23

项目工作台的「功能」入口已连接真实服务。功能话题可以在创建 Issue 前建立，支持按消息选择本机 Claude Code、Codex 或已有 API 连接。PostgreSQL 保存话题和消息，管理聊天 Worker 的本机日志保存每个话题和参与者对应的 AionCore 会话及发送回执。新参与者接收本话题最近窗口内已完成的讨论，页面可翻阅更早原文。

在已完成的回合下可以登记约定和待决定的问题。有效记录随话题传给后续参与者，结束后仍可查看原文。已用超过 24 轮的历史验证。

「本机讨论客户端」展示节点、探测时间和连接失败原因。点「重新检测」会请求节点重新探测该节点的客户端。原生客户端的认证状态指 Worker 到 AionCore 的连接；模型端回复以实际回合为准。话题支持取消排队或正在执行的回合，原生取消按发送回执定位。无法核实时页面显示结果待核实。会话丢失后，点「从话题记录恢复并重试」会生成带原回合编号的新回合，同一请求重复提交仍对应同一次恢复。

管理聊天 Worker 可通过环境变量 `FORGEOS_FEATURE_RESOURCE_WORKER` 关联实际执行节点的 Worker ID。该节点的模型并发上限同时计入讨论和开发执行；已配置的原生客户端账户配额也参与调度。本机已关联项目的 Windows Worker。

### P2 双方案与版本拍板 · 2026-11-23

话题的「方案与拍板」视图可单独打开。每轮以填写的需求、最近 24 个已完成讨论回合、当前话题记录、选定资料修订及仓库 HEAD 为输入。主控和顾问独立出稿，两稿齐全后主控逐项比较。可以向指定作者追问、只重试失败回合、修订综合稿，或修改需求另开一轮。每份原稿和每次确认都保留原来的轮次与修订。

本机 8080 的联调话题 6 使用 Claude Code 主控和 Codex 顾问，已保存两份原稿、综合稿和一次定向追问。综合稿修订到 v2 后，确认 v1 返回 HTTP 409。移动端确认 v2 后，控制面保存 Owner、确认时间及修订号，话题进入设计阶段。桌面 1440 像素显示双栏，390 和 320 像素窄屏显示单栏。隔离 PostgreSQL 验证了单方失败重试、同时交稿只触发一次比较、重复确认和另开一轮保留旧版。

### P3 单步骤设计、审阅、派工与回执 · 2026-11-23

确认方案后，主控自动起草，顾问审阅，再由主控整理含接口、意见处理与验收条目的定稿。升级前已拍板的话题可在「设计与交付」发起首稿。同一轮可以提交修订意见并重新送审；失败回合可以单独重试。已派工的版本保留完整的稿件与任务关联。

在定稿旁可创建项目 Issue 并派工，或选择本项目尚未开工的开发 Issue。控制面按项目、话题、方案修订和定稿回合核对，Worker 领取的任务包含这版定稿。工作台在原话题回读任务活动、执行状态、候选 SHA、预览与反馈入口、验收记录、PR 和合并 SHA。页面支持 `?view=delivery` 深链接。

本机 8080 的联调话题 6 已从第 1 轮方案 v2 接到设计 v1，依次完成 Claude Code 初稿、Codex 审阅、Claude Code 定稿，停在待派工。1440 和 390 像素宽度均已打开顾问意见和派工入口。按选定的联调范围，GitHub 写入与执行结果在隔离环境验证：模拟创建成功后响应丢失，重试恢复同一 Issue 和任务；验证已有 Issue 的 Worker 输入、失败回执，以及两次候选、验收退回、通过和合并回执。

## 1. 改造目标

你可以从一个还没想清楚的功能开始，选一个模型连续聊几天，邀请另一个模型独立判断，决定采用哪一版。之后在同一个话题里看设计、回答会影响范围的问题、试用候选版本、退回修改，最后查到实际发布的版本和验证结果。话题在创建 Issue 之前就存在，交付之后也能重新打开。

已确认的流程有两个常规人工决定。图中 **05** 确认这个功能要做成什么样，**10** 验收眼前这个可运行的版本。主控在两者之间组织工作。图中以 Claude Code 主控、Gemini 提供独立意见、Codex 实现后端并审查 PR 为例，模型分工随功能选择。一个需要整体联调的功能形成一个集成候选，合并前的返工更新同一张 PR。

先做一次 P0 接入验证，再分六批交付。P1–P3 让你隔天接着聊、看两个模型的独立判断、拍板后直接进入实际项目任务。P4–P6 打通协作实现、同一张 PR 的返工和上线核验。第 6 节列出每批可以亲手验收的结果。

## 3. 工作台和数据如何衔接

**工作台入口。** 在项目中增加“功能”列表，支持新建话题、继续最近讨论、查看等你决定的功能。进入详情即可看见当前阶段、谁在处理、等你做什么。讨论记录贯穿整个详情，旁边可以打开当前方案、设计稿、候选预览、PR 和发布记录。专项任务、计划、审查、CI 和日志仍有各自的详情，从两个方向都能跳转。手机端使用同一套入口和操作。

**客户端管理与模型选择。** 在节点的客户端列表里，你能看到 Worker 发现了哪些客户端、哪些已在该运行账户下验证可用，以及验证时间和失败原因。完成登录或更改配置后可重新检测。项目提供默认角色配置，你可以在每个功能内分别选择主控、顾问、实现和审查模型，也能在讨论中点名追问某一方。工作台显示本次选择的是本机 CLI 还是 API 连接。Worker 按实际能力认领，执行时固定运行器、所选模型和配置版本，结果附上运行器能提供的实际身份和会话记录。临时换模型只影响后续指派。顾问掉线时保留另一方已完成的提案，允许在同一份输入上重试或明确改派。

**接入方式。** 8080 工作台提供功能入口，ForgeOS 控制面处理用户身份、项目权限和阶段操作。所属节点的 Worker 通过本机认证连接调用 AionCore，让它发现客户端、创建或恢复会话、收发消息并报告工具活动。8080 的会话区优先复用可在浏览器运行的 AionUi 交互，身份和业务操作使用 ForgeOS 的接口。方案定稿后的代码实现由已有 Worker 在隔离工作树中承担。[项目工作台](../web/src/ProjectWorkspace.tsx) · [角色目录](../internal/agents/catalog.json) · [Codex 实现路径](../cmd/worker/codex.go) · [Claude Code 实现路径](../cmd/worker/claude.go) · [AionUi 前后端架构](https://github.com/iOfficeAI/AionUi/blob/main/docs/architecture/overview.md)

**职责。** 主控负责理解、比较、改稿、组织派工和解读结果。控制面负责保存版本和授权、推进状态、管理依赖与恢复。Worker 在获准的项目和工作树里执行。模型报告“已测试”时，工作台将其作为模型意见展示，检查结论取自实际命令、CI 或发布系统的回执。

## 4. 四个决定闭环能否成立的交接

### 4.1 同一份需求出两案，只有拍板版本进入设计

讨论阶段支持反复追问和主动结束本轮讨论。主控可在项目授权范围内查代码、资料、运行数据及已有线上证据，回答保留可回读的出处。隔天继续、切换设备或更换模型时，从功能记录恢复已定事项、未决问题、关联修订和最近对话，需要细节时回读原文。

功能讨论读取固定的项目资料和代码快照，按只读作业调度。功能 A 实现期间，你仍可与模型讨论功能 B。服务端按项目和话题检查每次读取，外部模型仅收到本次参与所需的资料与证据，凭据由已有凭据设施提供给对应运行器。

默认由你说“开始出方案”或点击同义操作来发起两案。控制面冻结同一份需求、证据和验收约束，为主控和顾问各开一个干净的提案会话，长期讨论仍可继续。两方各自交稿前，输入限于该快照及各自的角色任务，工作区内也应隔离对方草稿。两份都交回后，再把两份原稿交给主控逐项比较与解释，保留原稿供你追问。需求在出稿期间变化时保留旧稿，对新快照重新发起受影响的提案。

05 的操作同时展示方案版本、目标项目、允许开展的设计和后续派工范围。确认后自动进入设计。新反馈若改变功能范围或验收条件，生成新修订并交你拍板。普通问答、文案润色和范围内设计修整按已确认方向继续。

### 4.2 设计能派工，两个实现结果能合到同一版本

主控交出可查看的设计稿，顾问标注交互、文案及对应位置。最新版记录主控如何处理每条意见。07 给每个步骤指定模型、工作范围、接口版本、交付物和可验证的验收条目。可关联已有 Issue 或创建一张功能 Issue。多次点击、重复投递或创建成功后断线，都应恢复到同一个 Issue 和交付任务。

若功能属于已有 Goal，将该功能作为一个可交付项关联到父计划。前后端分工发生在这个交付项内部。沿用既有项目策略校验正式计划和授权范围，需要你重新决定的变化带着差异回到 05。[既有角色与决策](05-agent-roles-and-decisions.md)

对于图中的前后端协作，父交付任务占用一个项目写任务位置。实现步骤有各自的租约和隔离工作树，复用同一 Worker 调度器的任务、模型和 CI 名额。第一版将同一功能的写步骤安排在能访问同一登记仓库的节点，容量允许时并行，容量不足时排队。每个步骤交回登记过的 Git 引用和 SHA，集成时核对共同基线、接口修订和必要步骤。当前限制一个项目写任务的索引继续保护普通任务，实施时同步修订项目内协作的并发约定。[项目并发约定](adr/ADR-011-concurrency-policy.md)

父任务等待子步骤时只保留项目写入归属，把 Worker 执行位和模型名额交还调度器。只有一个可用执行位时，前端、后端和集成也能依次做完。候选进入人工验收后释放执行资源。

主控模型要写前端时，使用前端 Worker 的执行身份和独立工作树。集成由一个持有租约的执行者完成。冲突退到涉及的步骤，保留成功方的提交。联调命令、日志、预览与人工决定都绑定集成产生的具体 SHA。预览时提出的缺陷回 08，修改需求回 02。产生新候选后重新联调，并在 10 验收新版本。

### 4.3 已开 PR 的修正和两轮审查

第一次通过 10 后建立功能 PR。控制面登记稳定的 PR 标识、目标分支、预期头提交和已验收的候选。PR 上的 Codex 审查与仓库必需检查分别记录。候选验收前已有的代码审查可以为 10 提供依据，步骤 12 另按实际 PR 头提交组织审查。

第一次审查提出阻断项，原话题展示意见并派回对应步骤。修改形成新候选，经过 09、10 后更新原 PR，记录新旧 SHA，再跑审查和受影响的检查。更新前核对远端仍是预期头提交，发现外部推送或基线漂移时进入核对，重新集成和验收。控制面按仓库规则把新提交追加到原 PR 分支，保留其他人的改动。外部人员先行合并时，另记操作者来源并回读实际合并结果。

每张功能 PR 的一个审查周期最多两轮，跨候选修正累计。模型超时、重复 webhook、纯 CI 重跑按原尝试核对。第二轮仍有阻断就回原话题，由你决定继续修复、调整范围或终止。若决定开启新的审查周期，保留前一周期和裁决依据。只有当前 PR 头、最近有效的候选验收、当前审查结论、必需检查及分支保护同时满足时才合并。

### 4.4 发布与核验是两次可追溯的动作

对已启用发布的项目，在项目配置登记流水线、目标环境、版本识别方法和关键用户路径。首个适配器建议选用已有 GitHub Actions 发布流程的试点仓库，其他流水线可按相同的部署与验证回执约定接入。若合并本身已触发部署，ForgeOS 认领对应运行。若项目约定由 ForgeOS 触发，则登记意图后发起一次，并在超时后先向发布系统核对。项目发布凭据由现有凭据设施与流水线管理。项目已配置的环境保护、发布审批和权限由原发布系统执行，话题显示等待原因和回执。

13 记录合并 SHA，14 记录实际部署运行、目标环境和制品版本，15 验证线上版本与这次合并的映射，并运行约定的业务检查。只收到“部署成功”时显示“待线上验证”。部署失败可以重试同一制品。线上发现代码缺陷时，在原话题建立修复任务并另开修复 PR，保留已上线版本和故障证据。涉及回滚时使用项目已定义的发布策略。

建议对以“上线”为交付目标的新功能，在 13 反馈代码已合并，在 16 核验成功后关闭关联的功能 Issue。代码依赖仍可在核实合并后放行。已有普通 Issue、Goal 和仅要求代码交付的项目按原交付规则归档，功能页据实显示“代码已交付”或“已上线并验证”。实施该批时更新交付职责和 Issue 关闭两份 ADR。[交付职责](adr/ADR-015-code-delivery-scope.md) · [Issue 关闭约定](adr/ADR-017-issue-close-policy.md)

## 7. 旧数据迁移、发布和回退

1. **先部署向后兼容的数据和控制面。** 增加可空关联、新表、项目开关和 Worker 能力版本，再升级 Worker 和前端。旧客户端和旧 Worker 继续处理其支持的协议，新任务只派给具备相应能力的节点。用升级前数据库副本演练迁移和恢复。
2. **保留原始记录的含义。** 历史项目聊天展示为项目聊天历史。你可以把选中的消息、计划或 Issue 引入一个功能，记录原出处。正在执行的旧任务可链接进来观察，切换执行流程要有明确交接点。导入历史时以引用方式连接原记录，每次派工、审批、合并或发布沿用其原有身份。
3. **按项目逐批开启。** 先在一个可控的试点仓库打开新工作流，在 8080 实际走通该批验收，再扩大范围。项目自身的发布目标与 ForgeOS 工作台的 8080 部署分别核验。进行工作台升级时核实实际服务版本、Worker 能力和当前提供服务的前端资源，并在桌面与窄屏走查入口。[工作台验收约定](../web/AGENTS.md)
4. **按阶段回退。** 关闭新入口和新派发，先核对已经发出的 Issue、PR 和发布动作。已在运行的步骤由兼容版本完成或停在可恢复位置，旧工作流可继续使用。保留新增记录、发布回执和审计信息，重新启用后从最近确认的位置恢复。

## 8. 最终验收用一个真实功能贯穿

建议试点需求为“给项目列表增加名称筛选”。前端提供输入和清空，后端提供与查询条件一致的结果。已知数据可以检验命中、空结果和恢复全量三个行为。这个切片能同时检验讨论、前后端契约和部署后的真实体验。

- **讨论。** 第一天聊清使用场景，中间转去聊另一个功能，次日重开原话题。让主控和顾问独立判断筛选应放在哪里，查到两份原稿、观点分歧和 05 确认的版本。
- **协作。** 把带有筛选接口和清空行为的定稿交给两位实现者。一次工作树冲突或 Worker 中断后仍能接续，最后在同一候选上跑接口检查和页面检查。
- **退回。** 在候选预览中指出“清空后没有恢复全量”。看见反馈关联当前提交、修正后的新提交、重新执行的检查和你在 10 的验收记录。
- **交付。** 在打开的试点 PR 中走一次审查返工，核对同一 PR 的新旧头、审查轮次和合并提交。另用独立用例验证超限裁决。
- **演练上线。** 发布到项目配置的环境，核对线上制品属于刚才的合并，实际执行一次筛选和清空。错误版本即使健康检查返回成功，仍停在待核验。生产目标以其实际环境的回执验收。
- **回读。** 从原话题可以打开你的两次决定、两份方案、设计定稿、两个实现步骤、候选预览记录、PR、发布运行和业务验证结果，重启后仍能定位每一项。

工程验收包括真实 PostgreSQL 的迁移、并发与重试测试，Worker 适配器的契约测试和真实模型回合，前端构建、桌面及窄屏流程，以及真实试点仓库的端到端回执。数据库集成测试使用 `FORGEOS_TEST_DATABASE_URL` 指向专用测试库，检查跳过项。模拟提供方用于验证异常分支，真实模型、GitHub 和发布环境分别留存实际验收记录。[数据库测试入口](../internal/testdb/postgres.go)

## 9. 决策与实施默认值

- **已经确定。** AionUi/AionCore 承担功能讨论和多客户端会话。一个功能可挂多条会话，双方独立提案，05 确认方案，10 验收候选。实际派工、权限、候选 SHA、PR 和发布结果由 ForgeOS 控制面掌握。
- **首版交互默认值。** 开话题时可只选主控，出两案时再指定顾问。你明确发起后才调用两方。更换模型时保留旧记录和原话题，用新的参与者绑定接续。首批历史资料由你显式引用旧消息或任务。
- 第一版的前后端写步骤使用同一节点可访问的仓库，在独立工作树交付。跨机器传输未推送的步骤提交可以另行扩展。普通项目写任务与功能集成的互斥关系在 P4 验收。
- **按项目补充。** P0 核实试点 Windows 节点、运行账户以及可以真实调用的两个客户端。客户端需要交互登录时，由账户持有人完成对应登录。P3 选定允许创建试点 Issue 和 PR 的仓库。P6 再确定发布环境、实际版本来源、验证路径和凭据引用。以上环境信息分别在对应批次使用。
- 对以线上交付为目标的新功能，建议在 16 关闭功能 Issue。该策略与现有以合并为终点的项目并存，具体生效范围记录在项目设置里。

## 11. 功能工作台前端设计（已确认）

### 从哪里进入，回来时打开什么

在既有项目导航中增加「功能」。「聊天」继续承载项目级对话。功能列表显示话题名、主控、最近活动和等待谁行动，最近聊过和等你拍板的功能都能在这里找到。「新建话题」只需功能名称和首位讨论对象。旧聊天里选中的消息可以带着出处引用到话题。

桌面采用左侧话题列表、右侧功能详情。详情标题旁显示当前阶段，下面有「讨论」「方案与设计」「验收与交付」三个视图。日常续聊打开讨论，从“等你拍板”或“等你验收”进入则直达对应版本，再切回讨论仍是同一话题。窄屏先列话题，选中后用整页显示详情，返回时恢复列表位置。建议沿用工作台哈希路由，例如 `#/projects/{project}/features/{feature}?view=proposal`。从通知、预览或浏览器历史进入时恢复项目、话题和所看对象。[现有项目导航](../web/src/ProjectWorkspace.tsx) · [现有路由](../web/src/workbenchRoutes.ts)

### 首版界面与工程工单一起验收

1. **首版沿用已确认的交互稿。** 桌面用话题列表切换功能，手机从列表进入详情。讨论、方案比较和候选验收共用同一话题。功能详情沿用 ForgeOS 的暖色画布、白色面板、鼠尾草绿选中态、炭色主操作。模型选择沿用主题下拉框，AionUi 会话交互适配这一套工作台样式。[工作台界面规范](workbench-ui.md)
2. **P1.3 首次在 8080 验收持续讨论。** 在「项目列表名称筛选」中和 Claude Code 约定清空后恢复全量，在「停止后保留预览入口」中和 Codex 约定手动再次启动。关闭页面并重启试点 Worker 后，从桌面和手机分别回到两个话题，追问各自的约定。逐项核对原文、回复归属、所选模型和会话恢复方式。另验新话题空态、模型忙、验证失效、断线重连和发送结果待核对。提交结果不明时显示可核对的原操作。
3. **P2 交付比较和确认。** 在桌面并排打开两份原稿，在手机按作者依次查看，每种尺寸都能回到同一份逐项比较。用单方失败和双窗口版本冲突验证操作权限、失败提示及恢复位置。
4. **P3–P4 交付设计、预览与返工。** 验证从界面稿的顾问意见定位到修订，再从候选打开预览、提交意见、回原话题查看新 SHA 并验收。建立工作项时同步接入相应的前端入口和返回路径。
5. **P5–P6 交付后续证据。** 验证 PR 第二轮仍有阻断、部署成功但业务检查失败、上线核验通过三种显示。详情与列表摘要取同一条控制面记录。

正式实现按桌面 1440px、手机 390px 走查，并覆盖 320px 最窄布局、键盘操作和长标题。窄屏的讨论输入、方案确认、候选验收均可直接操作。后台刷新保留草稿和已有内容。深链接、版本冲突、权限与窄屏反馈分别用对应环境验证。每批在 8080 验收已接通真实服务的能力。

### P4 多任务实现与合成

在功能话题的「设计与交付」中，从设计定稿正式派工时可选「拆分任务并合成候选版本」。每次派工保存 2–8 项实现范围、执行客户端和模型选择。首次确认时建立一个关联 Issue 的总任务及其本地子任务。重复确认沿用原有分工。

执行节点须能运行所选客户端。子任务在同一节点从同一基线建立独立工作树，按任务位与模型位领取。各步骤完成时固定提交，合成执行保存每个输入的任务号、执行号与提交 SHA。Worker 按分工顺序执行 Git 三方合并，并对生成的整体提交运行项目验证。仅整体验证通过后进入候选预览与验收。

在原话题可查看每项的状态、错误、实现提交、本次合成清单及总任务的预览与验收记录。单项执行失败可以单独重试。合成冲突时可带修订意见重新派发对应步骤，保留其他步骤的提交，再生成新的候选。

### 工作台的可视审阅与交付进度

拍板前可为综合方案生成界面示意，点选控件提交修订后会保存新版本并重绘。已确认版本的可视稿随方案进入设计。设计草稿和定稿也各自保存界面示意。历史文字稿可请原作者按该回合补图。派工前，选择定稿中的控件并填写意见，会将来源版本、区域和控件随修订要求送回主控。派工登记时冻结当时的可视稿，与定稿一起提供给实现 Worker。

功能列表按实际任务、子任务、退回记录和合并回执展示阶段。多任务显示已交稿数和总数，点击话题可进入设计与交付详情。
