# ForgeOS 项目知识库设计

工作台入口为「项目 → 知识库」。已实现的维护流程、CLI 检索范围与版本规则见[项目知识与上下文服务](08-project-knowledge-and-context.md#项目知识库)。

## 入口与用途

在项目导航中增加「知识库」，与「项目资料」并列。「项目资料」继续用于读 Git 文档、维护 ForgeOS 资料和批量导入。「知识库」用于回答三个问题：这个项目确认过什么决定，有哪些经验还适用，哪些内容已经分享给了谁。知识库以当前项目为范围。资料和知识都可以单独存在，需要追溯时再通过证据引用关联。[项目知识双源管理](adr/ADR-004-project-knowledge-sources.md) · [项目知识隔离](adr/ADR-005-knowledge-isolation.md)

## 实施前的存储和维护方式

| 内容 | 原有 PostgreSQL 存储方式 | 原有维护方式 |
| --- | --- | --- |
| 项目决策 | `project_decisions` 保存决定原文、来源、适用条件、可选截止时间、证据及被替代的决定编号。`project_decision_events` 保存状态、操作人和时间，`project_decision_index` 计算当前状态。 | 对有效决定提出替代提案。Owner 确认时，新决定生效、旧决定被替代。历史编号仍指向原决定。 |
| 本项目经验 | 提取结果保存在 `material_curations.extraction` 的事实数组中。每条以提取记录编号和从 1 开始的事实序号定位。`current_project_experience` 选出经过 Management 审核通过、等级为 D1 且来源仍有效的记录。 | 「记住一条项目经验」会保存一份 Owner 记忆请求，再经过提取和审核。现在主要通过修订来源维护经验，缺少单独更正或撤回一条事实的入口。 |
| 跨项目共享经验 | `knowledge_shares` 每行对应一份发给一个项目的脱敏副本。它关联固定的 ForgeOS 资料修订，保存接收项目、脱敏标题与正文、内容摘要、审核记录、发布时间和撤销时间。 | 来源项目起草副本，Management 审核，Owner 发布。接收方只读已发布副本。修改内容会生成另一个待审副本，发布新版后，旧副本目前可能同时可见，需要单独撤销。 |

现有决策和共享入口位于「项目资料」的二级导航，已审核的本项目经验在资料管理中。共享的起点目前是 ForgeOS 资料的某个修订。接收方能在工作台搜索共享副本；当前工作区的任务 CLI 检索覆盖决策、本项目经验、ForgeOS 资料和 Git 文档四类。[决策表](../internal/store/016_decisions.sql) · [经验视图](../internal/store/093_experience_embeddings.sql) · [共享表](../internal/store/018_shares.sql) · [共享读写](../internal/store/shares.go)

## 界面如何维护

建议路由为 `/projects/{id}/knowledge`。页面顶部提供项目内搜索，按「项目决策」「项目经验」「共享经验」切换。决策和经验默认列出当前有效项，可切换「待处理」或「历史」。共享页提供「我发出的」「我收到的」。桌面左侧列出标题、状态和最近变更，右侧阅读选中项；手机先看列表，点入详情，返回时保留筛选和搜索词。

| 在哪里 | 详情里优先展示 | 主要操作 |
| --- | --- | --- |
| 项目决策 | 决定原文、适用条件、何时生效、证据与替代关系 | 提出决定、确认或拒绝提案、修订有效决定、标记失效 |
| 项目经验 | 一条经验陈述、适用场景、原文引句、来源是否仍有效、审核时间 | 记录经验、更正本条、撤回本条、查看修订差异、起草共享副本 |
| 我发出的 | 接收项目、实际对外展示的 Markdown、审核意见、当前发布版本 | 起草、根据意见修改、提交审核、发布新版、撤销当前发布 |
| 我收到的 | 脱敏标题与正文、发布时间、可引用的副本编号 | 搜索、阅读、复制本项目可用的引用 |

正文编辑支持 Markdown 预览与原文切换。点「修订」时展示当前版与拟议版的差异；保存后明确显示「待确认」「待审核」或「待发布」。详情保留「版本与依据」入口，可查谁在何时确认了什么。旧决策链接、共享回执链接和计划引用继续按原编号打开。

例如，A 项目把「重复导入时按来源和内容识别」分享给 B。A 可以先改脱敏说明，此时 B 仍看到已发布的第一版。第二版审核通过并由 A 发布后，B 在同一个共享条目下看到新版。如果 A 撤销，B 的后续搜索和新任务引用都失去该条目。B 无权通过副本打开 A 的私有原文或审核笔记。

## 建议的数据结构

保留各类业务记录作为写入依据，用 PostgreSQL 视图提供统一列表。每个对外引用都区分「日常打开的条目」与「当时读到的修订」。下表是拟议变更。

| 对象 | 主键与关键字段 | 用途与约束 |
| --- | --- | --- |
| 决策与事件（沿用） | `project_decisions.id`、`supersedes`、`project_decision_events.decision_id` | 每次替代已有独立决定编号。库内按替代链归组，待确认的替代提案与当前有效决定并列展示。旧计划里显式引用的决定继续遵循现有的有效性检查。 |
| `experience_entries`（新增） | `project_id, id, current_revision, withdrawn_at` | 一条可独立维护的本地经验有一个稳定编号。撤回仅作用于本条。 |
| `experience_revisions`（新增） | `project_id, entry_id, revision, based_on_revision, curation_id, fact_number, change_reason, actor, created_at` | 一个已采纳修订指向一条审核过的事实。陈述、引句和证据来自该事实的固定回执。条目、修订及提取记录用同项目外键约束，每个已映射的事实只能对应一条经验修订。 |
| 私有经验更正请求（新增关联） | 请求编号、经验编号、预期当前修订、独立的记忆请求资料修订、提交人、处理结果 | 更正时可以先保存和送审，保留原有效版。审核完成后绑定具体的新事实；若一次提取出多条建议，由维护者选择对应事实。通过同一事务追加修订并切换当前指针。新经验沿用相同的记忆请求和审核入口。 |
| `knowledge_share_series`（新增） | `id, project_id, recipient, current_share_id` | 一条发给指定项目的共享关系有稳定编号；不同接收项目各自发布、更新、撤销。 |
| `knowledge_shares`（扩展） | 现有副本编号、摘要和审核回执，增加共享关系编号、版本号及被替代副本编号 | 每版有独立脱敏正文和审核。来源可选固定的资料修订或已审核的本地经验修订，两种外键恰选其一。当前指针必须属于同一发送项目、接收项目与共享关系。 |
| 知识库列表（新增只读视图） | 当前项目、类型、稳定编号、修订引用、标题或摘要、状态、最近变更 | 从上述领域记录投影。私有条目与接收副本分别校验可见性后再合并、分页和统计。接收视图只投影已获准披露的字段。 |

### 更新与检索的一致性

- **更正经验**。同一批提取出三条经验时，每条有独立身份。改第二条只切换第二条的当前修订。即使条目处于启用状态，检索也要核对底层来源仍然有效；来源失效时，详情显示原因并允许补充证据。
- **更新共享**。发布事务核对 Owner 所在项目、接收项目、预期旧版本和这次通过审核的内容摘要，再切换当前指针。旧副本保留源端回执。接收方列表、关键词和向量检索都按同一个当前发布条件过滤。两个窗口同时发布时，后提交者看到版本冲突并保留草稿。
- **明确权限**。Owner 确认或替代项目决策，Management 审核经验；跨项目发布须经过独立审核和 Owner 发布。新正文来自资料或聊天时仍保留来源和引句。接收项目的 API、计数、摘要和搜索结果都只使用脱敏副本字段。[知识更新权限](adr/ADR-018-knowledge-update-authority.md)
- **任务采用**。建议为 CLI 增加第五类来源「收到的共享经验」。搜索、读取和采用时分别按接收项目检查当前发布版本。若读取后、采用前发生撤销或换版，则提示重新检索。撤销前已采用的历史任务保留当时获准的脱敏引句、版本和摘要，回看时标出后续状态；后续任务遵循当前可见性。共享经验始终标为参考，项目约束以本项目有效决策为准。

## 落地顺序与验收

1. **先集中入口**。复用现有决策、经验、共享接口，把列表、搜索、详情和已有维护操作接到知识库。资料页保留「查看关联知识」入口。第一步即可用真实数据验证导航和权限。
2. **再补独立修订**。已有决策沿用原编号。按 `(project_id, curation_id, fact_number)` 幂等映射已有经验，同时保留历史有效性。旧共享副本各自建独立共享关系；历史上没有明确替代关系的记录保留各自身份。修订写入支持幂等请求和预期版本校验。
3. **最后接入跨项目任务检索**。旧工作台链接和已有任务证据继续按固定版本回读。验收时用两个项目验证发布、换版和撤销，再验证本项目更正单条经验、驳回修订、并发修改，以及历史任务的原文回读。共享的接收端在整个流程中都只能看到获准发布的字段。
